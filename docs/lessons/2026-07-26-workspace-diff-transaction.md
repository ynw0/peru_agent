# Workspace、Diff 与 Checkpoint 可复用经验

## 现象一：`**/*` 没有匹配工作区根目录文件

### 根因

简单把 `**` 翻译成 `.*`、把 `/` 保留为必需字符，会让生成的正则要求至少存在一层目录。

### 修复

`**/` 必须翻译为可选的零层或多层目录：`(?:.*/)?`。

### 可复用规则

Glob 语义必须覆盖根文件、嵌套文件、空目录层级和 Windows 路径输入，不能只测试嵌套路径。

## 现象二：一次哈希检查不足以保护文件

### 根因

在检查哈希后写临时文件期间，用户或其他进程仍可能修改目标文件。

### 修复

- 每个工作区内部文件修改串行化；
- 写临时文件前检查一次哈希；
- `rename` 前再次检查哈希；
- Diff 接受前一次性检查所有文件。

### 可复用规则

任何“检查后写入”的逻辑都必须考虑 TOCTOU；应用层必须缩小时间窗口，操作系统级安全仍由 Sandbox Broker 负责。

## 现象三：模型提出修改不应等同于拥有写权限

### 根因

若 Write Tool 直接声明并执行 `workspace.write`，用户必须先批准工具，之后又要审核 Diff，形成重复权限流程；若自动允许，则模型获得了真实写权限。

### 修复

增加独立的 `workspace.propose` 能力：模型只能生成 Proposal，真实写入由 IDE 的接受动作完成。

### 可复用规则

“提出副作用”与“执行副作用”必须使用不同能力，权限系统不得把预览操作当作真实写入。

## 现象四：多文件写入和恢复可能留下半完成状态

### 根因

逐个写文件时，后续文件失败会让前面的文件已经改变；Checkpoint 恢复同样存在该问题。

### 修复

- 写入前检查全部文件；
- 保存修改前和修改后内容；
- 写入中途失败时按反向顺序回滚；
- Checkpoint 恢复中途失败时恢复到接受后的状态。

### 可复用规则

多文件操作必须定义事务边界、补偿数据和回滚测试，不能只依赖“通常不会失败”。

## 现象五：JSON 持久化文件不能只做 TypeScript 类型断言

### 根因

磁盘文件可能损坏、被手工修改或来自旧的不受信任内容，`as DiffProposal` 不会在运行时验证。

### 修复

Diff 和 Checkpoint Store 在读取 JSON 后执行结构校验，不符合当前协议时明确失败。

### 可复用规则

文件、IPC、网络和插件边界均属于不可信输入，必须运行时验证。
