# 发布签名、原子更新与本地化经验

## 根因一：历史测试写死当前协议版本

历史测试将 IPC Version 或 Workbench 容器数量写死，会把合法新增能力判定为回归。

**规则：**历史契约验证最低协议版本、必需方法和稳定容器位置，不固定未来可增长的精确数量。

## 根因二：Overlay Stub 与真实 Code OSS API 不一致

本地 Stub 缺少真实 1.74.0 已存在的 Codicon 时，会产生假编译失败。

**规则：**Stub 必须同步固定上游版本；最终判断以原始 Code OSS 源码上的 API 契约验证为准。

## 根因三：签名 Manifest 与 Authenticode 不是同一信任层

Manifest 保护文件集合和版本语义；Authenticode 保护 Windows PE 发布者身份。只实现任意一个都不足以发布。

**规则：**生产 Windows 发布同时要求 Ed25519 Manifest 和有效 Authenticode。

## 根因四：普通更新允许降级会绕过发布策略

若正常 Update 接受旧版本，攻击者可以利用仍有效的旧签名进行版本回退。

**规则：**普通更新只允许版本严格上升；降级只能通过显式、可审计的本地 rollback。

## 根因五：仅检查字符串路径不能阻止符号链接

Bundle 内相对路径合法不代表真实文件仍位于 Bundle 根目录。

**规则：**根目录、Payload 和 SBOM 必须检查 `lstat + realpath`，读取前后重新确认真实路径没有变化。

## 根因六：本地化静默回退掩盖缺失资源

缺失 Key 或参数若回退到另一语言，会在测试中隐藏不完整界面，并可能显示错误安全提示。

**规则：**Catalog Key 和插值参数严格一致；未知 Locale、缺失和多余参数全部失败。

## 根因七：原子更新的关键是最后切换指针

直接覆盖当前目录会在进程中断时留下半安装版本。

**规则：**先完整验证并写入新版本目录，最后原子更新状态指针；失败不触碰当前版本。

## 根因八：发布脚本不能把“构建成功”等同于“可发布”

未签名的 Setup 或未验证的 Payload 即使能运行，也不满足发布要求。

**规则：**签名或验证失败时删除发布输出；生产门禁未全部通过时 Readiness 必须为 blocked。
